# P22 — Bioequivalence as data

**Before starting:** read `docs/target-toc.yaml` (`be_study_model`, and leaves 1.2.17, 1.2.18, 1.4.1, 5.2, 5.3.1.2), `app/models/clinical.py`, the `generic_requires_bioequivalence` rule, and `reference/nafdac-vs-fda-ema-scope.md`. Depends on P18 — the study report itself is an uploaded document.

## Goal

Unblock **5 leaves**, including the single most important document in the target. For a multisource filing, 5.3.1.2 carries the entire scientific argument for approval.

## The problem, stated precisely

`ClinicalEntry` is `kind` + `reference_product` + a free-text `summary`. The `generic_requires_bioequivalence` rule can therefore check only that a row exists.

Nothing can check that the 90% confidence interval for Cmax and AUC falls within the accepted range. Nothing can check that the reference product named in the study is the one named elsewhere in the dossier. And 1.4.1 — the Bioequivalence Trial Information form — is generated *entirely* from study data, so it cannot exist at all while that data is a paragraph.

## Tasks

### P22a — The study as structured data (backend)

1. **A `BioequivalenceStudy` model**, replacing or extending `ClinicalEntry`:
   - Design (crossover, parallel), fasting or fed, single or multiple dose
   - Reference product: name, strength, manufacturer, country of origin, batch number, expiry — a *reference*, not a string, so it can be cross-checked
   - Test product batch, batch size, and manufacturing date
   - Subject count, dropouts, analyte measured, bioanalytical method
   - CRO name and study site
   - Per-parameter results: Cmax, AUC(0-t), AUC(0-inf) — each with a geometric mean ratio and a 90% confidence interval lower and upper bound

2. **Register the sections**: **5.3.1.2** (uploaded study report plus a structured summary rendered from the data), **5.3.1.4** (uploaded bioanalytical method reports), and **5.2** Tabular listing of all clinical studies — generated by walking the studies present, so it cannot disagree with what is actually filed.

3. **1.4.1 BTI form**, generated with no prose. It is a Module 1 document produced entirely from Module 5 data, which makes it the clearest demonstration in the whole platform of why the single-source-of-truth premise matters.

4. **The rules this unlocks:**
   - A 90% CI falling outside the accepted window is an ERROR naming the parameter and the bound. Put the window in region config, not in the rule body — acceptance criteria are regulatory parameters and they change, and narrower windows apply to narrow-therapeutic-index drugs.
   - The reference product named in the study must match the one named in 1.2 and 2.3. This is the cross-module check the platform was built for.
   - Test product batch size must be a defensible fraction of the proposed commercial batch size in 3.2.P.3.2 — cross-module, and a genuine regulatory finding.
   - A biowaiver claimed in 1.2.17 or 1.2.18 and an in vivo study filed for the same strength are mutually exclusive. Exactly one route must be present.

5. **Multiple strengths.** 1.2.18 is a biowaiver request for an additional strength, so it presumes a filing can span strengths. Check whether `Project` and `Product` can represent a product family. If not, say so plainly in the build log rather than working around it — this constraint will resurface, and it is cheaper to name now than to discover during a real filing.

### P22b — Study entry and the biowaiver decision (frontend)

6. **A BE study step** in the wizard: study design fields, reference product, and a results grid for the three parameters with their confidence intervals. Show pass or fail against the acceptance window as the numbers are entered.

7. **The biowaiver decision as an explicit choice.** For each strength: in vivo study, BCS-based biowaiver, or additional-strength biowaiver. The choice drives which leaves become applicable, through P17's applicability profile — this is that machinery earning its keep.

8. **Upload the study report** against 5.3.1.2 through P18's upload path, alongside the structured summary.

## Definition of done

- `scripts/check_target_toc.py` gains 5 leaves.
- A test proves an out-of-window confidence interval blocks export and names the parameter.
- A test proves a mismatch between the study's reference product and the dossier's reference product is caught.
- 1.4.1 renders from study data with no hand-entered content, and a test proves it cannot disagree with 5.2.
